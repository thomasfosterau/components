# @thomasfosterau/components-import

The data import mapper of #139: an app hands it a target `Schema.Struct` and a user's table, and gets typed records back, row by row, with every issue tied to a field and a source cell. The `.` entry is its headless core; `./svelte` is its UI (`ImportMapper` and its step components). Repo-wide rules are in the root [AGENTS.md](../../AGENTS.md); the entry is in [README.md](README.md); the API reference is the TSDoc on each export. The issue is the spec, its later comments overriding the body.

## Where it differs from the other packages

It has packages/charts' shape (see [its AGENTS.md](../charts/AGENTS.md)): plain TypeScript built with `vp pack`, then `svelte-package` for `./svelte` alone (`src/svelte` into `dist/svelte`, as `.svelte` source); `check` as the Effect-patched native `tsc` twice (`tsconfig.json`, then `tsconfig.pure.json` over the core with no DOM lib and no ambient types), then `svelte-check` over the UI, its stories and its suite (`tsconfig.svelte.json`); and a Node suite for the core. What it does not take from charts, and why:

- **Effect is the public API, not an implementation detail.** `importTarget` returns an `Effect`, `applyMapping` a `Stream`, the spec and descriptor are Effect Schemas and the errors are `Schema.TaggedError`s. So `effect` is a required peer (`catalog:peers`, `^4.0.0`) rather than a dependency, and there is no `check-dist-types` script: the published `.d.mts` names `effect` on purpose. `@thomasfosterau/effect-document` is the other (`catalog:peers`, `^0.2.0`), for the same reason: `sourceTableFromRegion` and `findRegion` take the app's own `TableRegion`s and `Document`s, and `TableLocator` is its type. The code is developed on the workspace pin and written to run on 4.0.0.
- **The core, its suite and `src/svelte/session.ts` are Effect code** (`effectFiles` in the root `vite.config.ts`), so every Effect lint rule applies to the suite too. The `./svelte` components and their browser suite are not: they are the UI side of the promise boundary below, Svelte code with `T | undefined` props that awaits `session.ts` in `try` / `catch`. `session.ts` keeps `T | undefined` on the types the components take as props, and is where each Effect is run.
- **The UI has stories and a browser suite, as the Svelte packages do.** Its stories live in `src/stories` (rendered by the one Storybook in packages/components, whose `stories` glob reaches here; `storybook:build` depends on this package's `build`), and its suite in `tests/svelte` runs in Chromium under Vitest browser mode from its own config, `vite.svelte.config.ts`, since one Vitest config is either Node or browser mode. `test:unit` runs the Node suite, then the browser one.
- **`@thomasfosterau/components` is a `workspace:*` dependency**, as in packages/mapbox: the UI's fields, buttons and `Steps` come from its root entry, which resolves through its `exports` to its built `dist/`, so `check`, `build` and `test:unit` depend on its `build`.
- **Published from slice 3.** Slice 3 removed `"private": true` and added the package's first changeset. Its first publish needs the owner's one-time npm bootstrap ([PUBLISHING.md](../../PUBLISHING.md) §3) before a Release run can publish it.

## Boundary

- **The `.` entry is headless.** No Svelte, no DOM, no Node: `fallow-rules.json`'s `import-core-independent` bans `svelte`, `$app`, `$env` and the other workspace packages from `src`, and `tsconfig.pure.json` fails `check` on any DOM or `node:` reference. An app server imports the same module to re-decode, and the engine can move into a Web Worker later: its inputs (`ImportSpec`, `SourceTable`, `CellEdit`s) are plain data.
- **Callbacks that cross into the UI follow the repo convention** (`(…, signal: AbortSignal) => Promise<T>`), so an app's UI code never touches Effect; the Effect surface is for the app's own Effect code and its server. `src/svelte/session.ts` is that boundary: each step's Effect work (`detect`, the reader, `applyMapping`) behind a promise that takes an `AbortSignal`, its failure a `StepError` with a message for the user.
- **`./svelte` reaches the core by the package's own name** (`@thomasfosterau/components-import`), never by relative path, because `svelte-package` copies `src/svelte` alone; `tsconfig.svelte.json`'s `paths` and `vite.svelte.config.ts`'s alias point it at the source for `check` and the suite. It loads no reader: the app passes the formats it accepts (`ImportFormat`, which every effect-document `Format` satisfies), so `fallow-rules.json`'s `import-ui-boundary` bans effect-document's reader subpaths and `@thomasfosterau/effect-parse` from `src/svelte`. Its targets are `ServiceFreeTarget`s, structs whose decoding needs no Effect service, which every supported field kind is.
- **Documents come from `@thomasfosterau/effect-document`, through `/schema` only.** `src/region.ts` is the adapter: `sourceTableFromRegion` reduces a `candidateTables` region (a `WorksheetRegion` or a `ProseTableRegion`) to the neutral `SourceTable` through the same header/skip reading as `sourceTableFromGrid` (`sourceTableFromRows` in `src/table.ts`), `regionRead` is the region's own header guess, and `findRegion` finds the region a spec's `source.table` names. `TableLocator` is upstream's type; the Schema here decodes a stored one, and `tests/spec.test.ts` pins the two mutually assignable. `src` imports no reader subpath, so effect-document's optional peer `@thomasfosterau/effect-parse` (the `/csv`, `/rtf`, `/ooxml*` and `/iwork*` grammars) is not ours: an app takes it on when it imports a reader. It is a devDependency here because the suite reads CSV through `/csv`. `fallow-rules.json`'s `effect-document-only-in-import` keeps effect-document out of every other package.
- **How a worksheet cell maps** (`src/region.ts` says it on `sheetCellValue`): to the value a CSV export of the sheet would carry, so a workbook and its CSV map alike. Text, number and boolean their value, a date its `Date`, a formula its cached result (none without one), rich text its plain text, an error its literal (`#DIV/0!`, which `parse.nullValues` can empty), a blank or a gap no value. A row the sheet does not hold is no row, and a row's `index` is the sheet's row index. A prose table's covered (merged-over) positions are no value; a header position under a merged cell, in either kind, takes that cell's text.
- **`sideEffects: false` holds**: every module only declares. The transform registry (slice 5) will be a value the app constructs, never a module-level map.

## Invariants

- **`ImportSpec` version 1 is fixed.** It already carries every `FieldMapping` kind and every `ParseOptions` field, so a stored preset decodes the same before and after the engine learns them. A change to its shape is a `version` bump with a migration, never an edit. `decodeImportSpec` is strict (`onExcessProperty: 'error'`, every issue collected).
- **JSON-document types are present-or-absent.** `ImportSpec`, `FieldDescriptor` and `TargetDescriptor` use `Schema.optionalKey`, never `| undefined`, as packages/charts' spec types do; the code builds the descriptor with `Option` (`Schema.OptionFromOptionalKey`) and encodes it.
- **An unsupported kind is an error, never a skip.** `importTarget` fails with `UnsupportedFieldType` on a field no single cell can fill; `applyMapping` fails with `UnsupportedMapping` on a mapping kind it does not apply yet, before any row.
- **Rows decode through the target's own Schema**, as `Schema.toCodecStringTree(target.schema)`: every cell goes in as its canonical text (a `Date` as ISO 8601), so typed worksheet cells and prose-table text decode alike and the target's checks run unchanged. A row's `index` is its position in the whole table, so edits and issues survive a change to `skipRows` or `headerRow`.

## Testing

`vp test run tests` under Node for the core: decoding and mapping, no DOM to drive. `vp test run --config vite.svelte.config.ts` for the UI, in Chromium: each component's ARIA contract (names, `aria-current`, focus on step change, live regions) and one test per `ImportMapper` path. Its fixtures read CSV through `/csv` too, and a test passes props under `props:` because `target` is a Svelte mount option (AGENTS.md § Conventions). `render` instantiates a generic component at its constraint, so the type link from the target to `onSubmit`'s `records` is pinned by svelte-check over `ImportMapper.stories.svelte` instead. Documents are built with effect-document's constructors, or read from text through its `/csv` reader (`tests/region.test.ts`, a preview `maxRows` read included). Tests import `it`, `describe` and `assert` from `@effect/vitest` (`it.effect` for anything that runs Effect, plain `it` for pure helpers), which wraps the workspace's one `vitest`, the copy `vite-plus/test` re-exports; nothing imports `vitest` directly. `tests/` mirrors `src/`.

## Commands

From the workspace root:

```sh
vp run --filter ./packages/import test:unit   # Vitest under Node, then the UI in Chromium
vp run --filter ./packages/import check       # tsc, the DOM-free re-check of the core, svelte-check
vp run --filter ./packages/import build       # vp pack -> dist/, svelte-package -> dist/svelte
```
